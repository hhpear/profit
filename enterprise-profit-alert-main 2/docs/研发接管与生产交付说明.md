## 1. 研发要完成什么

现有任务每天08:00（Asia/Shanghai）由寇誉博个人电脑上的Codex自动任务触发，处理昨天完整自然日的数据：获取国内BMP、国际Pigeon企业客户利润，按日历基线判断异常，通过飞书卡片通知金长春、寇誉博、李童晶、刘嘉玲；零业务告警时不发送业务卡片。

目标是交付可由公司独立运行和维护的服务器任务：使用公司服务身份取数、公司管理的机器人发送、服务器固定程序调度，并具备监控、暂停、恢复和防重复能力，不依赖创建者电脑、浏览器会话、个人模型或个人凭据。

利润算法、阈值、业务卡片内容及正式通知范围保持不变。研发可复用、改造或重写现有代码，不要求保留AI编排或DeerFlow。

## 3. 接收后先做什么

李祖定首先检查仓库访问权限、资料和代码，反馈能否承接、复用/改造/重写建议、工作量、资源依赖及排期。目前其实际仓库权限与承接结论尚未核实；访问有问题时协调仓库管理员处理。

在有权限的开发环境使用Python 3.11+做初步检查：

```bash
git clone https://github.com/yuexin-dev/enterprise-profit-alert.git
cd enterprise-profit-alert
git rev-parse HEAD
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python3 scripts/validate_enterprise_profit_alert_governance.py
python3 -m unittest scripts.test_enterprise_profit_alert scripts.test_enterprise_profit_alert_domestic
```

上述命令只做静态校验和核心测试，不进行真实取数或发送。已有核心50项测试和静态校验通过记录，研发需在接收环境重新运行。完整CLI及依赖版本仍需研发锁定。可选DeerFlow测试缺少未上传的历史快照，另有已登记日期被当作未登记日期的旧断言；不得将全部测试直接可通过当成交付承诺。

承接后建议通过接管Issue跟踪排期、任务和问题，代码走分支及Pull Request。当前没有创建接管Issue、指派任务或向研发发通知；这些协作动作未完成，不影响对现有资料进行评估。

## 5. 测试及一周试运行

### 技术测试

| 场景 | 通过条件 |
| --- | --- |
| 正常、阈值边界、正转负、持续下降、零告警 | 结果与既定规则一致；单日普通下降只观察，利润上升不发业务告警 |
| 缺页、缺金额、身份缺失、样本不足、日期或规则不符 | 失败关闭或明确不判断，不补零或用旧数据伪装成功 |
| 未授权身份/对象、撤权、错误机器人或收件人 | 拒绝执行，不换个人身份或接口绕过 |
| 重复触发、换目录、跨机、重启、部分发送后崩溃 | 已确认消息不重复发送；发送超时结果未知或回读失败时先查证，不盲目重发 |
| 来源中断、漏跑、卡住、存储或通知通道故障 | 能发现、通知、暂停并恢复，失败有记录 |
| 备份恢复和回退 | 历史及发送状态可恢复，不补发旧日告警 |

故障模拟在隔离环境进行，不破坏线上系统或向正式对象制造错误告警。研发记录测试提交、场景、预期、实际、结果和问题链接。脱敏摘要不能代替计算测试输入，需使用授权输入或合成数据。

### 连续一周试运行

旧环境继续正式通知，公司环境只向创建者和指定研发人员试发。开始前双方确认连续7个自然日的起止时间；实质故障后是否重计窗口共同确认。

每天记录数据日、代码/规则版本、运行状态、异常数、与旧结果的差异、测试通知结果及问题编号。详细客户金额和消息记录保存在授权位置，不整包上传GitHub。

通过条件：没有未解释漏跑；同一输入下企业利润、基线、异常名单、趋势及卡片业务内容一致；仅测试人员收到带测试标识的消息且完成回读；零告警时测试人员收到运行状态，正式对象不收业务卡片；不存在未解决的数据错误、错发、重复发送、权限或恢复问题。

比较优先使用同一授权快照，避免取数时点变化及查询次数翻倍；正式切换前，公司环境须证明可独立取数。若一周没有真实异常，使用授权合成或脱敏输入验证卡片和投递，不改真实数据或阈值制造异常。

## 6. 正式切换及维护

技术测试和一周试运行通过后，李祖定给出技术结论；寇誉博核对业务结果并批准切换窗口和首个正式数据日。

1. 停止旧任务并确认没有仍在发送的进程，核对最后已发送日期及结果未知的消息。
2. 研发同步历史与发送状态，启用公司应用正式名单和唯一调度。新身份/投递配置单独版本化。
3. 核对首个正式结果与消息；零告警时确认运行成功且未发业务卡片。记录切换完成，旧任务保持停止。

数据错误、错发或重复发送时，李祖定可立即暂停并通知寇誉博；优先修复或回退公司稳定版本，验证后由寇誉博批准恢复。是否更正已发送的错误消息由业务负责人决定。本机旧任务仅为应急备选，未经单独批准不得自动恢复或补发旧日告警。

上线后李祖定承担技术维护、故障处置和日志管理，寇誉博负责业务规则及效果确认。按工作时间响应、失败通知技术负责人并让业务负责人知情，当天恢复或说明原因；具体工作时段、响应时限和备用联系人由研发承接时落实。

研发最终交付：公司仓库正式版本、部署启动及调度配置、权限和密钥管理位置说明（不写密钥）、测试及一周试运行结论、暂停/恢复/回退操作、维护联系人及技术和业务切换确认。完成标准是公司能够独立运行并维护。
