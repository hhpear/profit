## 调度与执行

当前是创建者个人电脑上的 Codex 每日自动任务，状态 ACTIVE，每天08:00（Asia/Shanghai）处理前一个完整自然日。任务名“企业客户利润异常告警每日任务”，配置使用 gpt-6.1-sol / medium；执行链由自动化提示词编排，并非独立服务器调度。ACTIVE配置不能证明每日准时启动；近30天实际结果见[月度记录](examples/recent-30-days/README.md)。

执行目录为创建者的 kanban 工作区。告警生产入口在工作区根目录 scripts 下；经营看板 canonical 项目仅提供被引用的 MCP 客户端。不能把看板执行根与告警执行根混为一谈。

1. 读取业务文档、当前告警 active.json 及其不可变规则，运行告警静态治理校验。独立告警不以前置经营看板全量治理为门禁，但须校验所引用经营规则的指针及SHA，仅使用国际测试和历史通道排除项。
2. 设置数据日为昨天。找到最新兼容 SUCCESS history，确保其来源、日期和规则可用；从 history.coverage.end 下一日起连续补齐 Pigeon 日回执至当前数据日。
3. 通过批准的 LiteLLM MCP 工具获取 Pigeon 全日数据，按企业/账号/通道聚合。每天正常查询一次；传输/包装/落盘失败最多重试2次。当前目录已有合法回执时验证后复用；来源错误失败关闭。历史恢复只补输入，不补发旧日告警。
4. Runner 获取 BMP 近60天历史及当日明细，完整分页校验；计算异常，生成 history、alert、Card 2.0、投递回执和run manifest。
5. 有业务告警才投递正式范围，发送后核对身份、接收人和内容；零告警保存0消息回执。manifest及投递回执都成功才算运行成功。已有成功目录只核验，不重复查询/发送。
6. 失败记录阶段、数据日、规则和查询/消息次数并停止；不补零、不换来源或身份、不盲目重发。恢复后沿用已验证回执，经原入口处理当前日。

## 参数示例（占位符，未执行）

以下是现有个人环境的调用形状，不是新机器可直接使用的部署命令。DAY、RUN_DATE由Asia/Shanghai日历确定，HISTORY由校验后选择；历史不能只按文件修改时间选择。

```bash
python3 scripts/validate_enterprise_profit_alert_governance.py
python3 scripts/fetch_enterprise_profit_alert_pigeon.py \
  --previous-history "$HISTORY" --current-day "$DAY" --output-dir "$OUT"
python3 scripts/run_enterprise_profit_alert_daily.py \
  --current-day "$DAY" --output-dir "$OUT" --previous-history "$HISTORY" \
  --international-receipt "$RECEIPT_DAY_1" \
  --international-receipt "$RECEIPT_DAY_2"
python3 scripts/validate_enterprise_profit_alert_governance.py --output-dir "$OUT"
```

OUT形如 `outputs/enterprise-profit-alert-daily-<RUN_DATE>-for-<DAY>`。连续回执从历史结束日下一日至DAY，按日期排列，每日重复一次 `--international-receipt`，不固定只有两份。冻结输入预览用 `--history <已校验history> --dry-run`；dry-run不发送，不能代替投递验收。普通Runner有异常时的 `--acceptance-test` 会拒绝执行，测试发送须遵循既有单人sender流程；公司试运行的多测试人投递需研发改造。
